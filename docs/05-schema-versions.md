# 05 — Schema versions

How a database's schema follows the entities: what is in `src/Schema/`, what must stay true, and
where the drivers differ. The user's side — `call db snapshot`, `#[EnablePpaMigration]` — is the
kernel's (`console/Command/Db.php`, `src/Ppa/PpaSchema.php`); this package holds everything that
does not need a framework.

## The idea in one paragraph

The entities are the only description of the schema. A **snapshot** freezes what changed since the
last version into `ppa/<Config>/V<nnn>_<name>.json` — that version's changes only, never the
whole schema. Folding the versions in order gives the **model** of any version, in memory, with no
database. A database applies the versions it lacks; a fresh one is created from the last model at
once. Nothing is written by hand except a version's **code** (`custom/V<nnn>_<name>.php`), for
what a snapshot cannot say.

## The folder

```
ppa/
  PgDb/                              ← the config's short class name, as it is
    V001_init.json                   ← generated by `call db snapshot`, never edited
    V002_add_status.json
    V003_client_user_set.json
    custom/
      V003_client_user_set.php       ← written by a person: class V003_ClientUserSet
```

- `ppa/` holds nothing but database folders; whatever a database gets later (seeds) goes inside
  its own folder. The kernel names the folder (`PpaSchema::nameOf()`), and points at a folder of
  versions that no config is named after — a config renamed without its folder.
- A version is `V` + a number of three digits at least: the next is the last number + 1
  (`SchemaDirectory::nextVersion()`), no clock involved. The files sort as they apply up to
  `V999`; past it, `SchemaDirectory` and `SchemaHistory::rows()` order by the number.
- Two branches that took the same number meet as "V008 is there twice" — one is renumbered. One
  renumbered after the other was applied arrives *late* (older than the last applied, never
  applied) and is refused: record it again.
- A version's code is in the namespace of its config (`namespace App\Config\PgDb;`, given by the
  kernel): two databases — or an application and a package — may each have a `V003_FillStock`, and
  one process loads both. Not in PSR-4: the kernel includes the file when the version runs, and
  finds the class by its `#[SchemaVersion]`, not by its name.
- `winter_ppa_schema_history` is keyed by `(owner, version)`: two configs on one database, or an
  application and a package, keep their histories apart, each with its own `V001`.
- Every JSON of the folder must be a version, and every PHP must be in `custom/`, named after a version
  that says `"code": true` — a file in the wrong place is said, not passed over.

## The parts

| Class | What it does |
| --- | --- |
| `SchemaModel` | the model as plain arrays: from the entities' `Structure\Table` (`declared()`), one change applied (`apply()`), a history folded (`fold()`) |
| `SchemaDiff` | the changes from a folded history to the declared model — or why they cannot be recorded |
| `SchemaSql` | the statements of a change for `pgsql`, `mysql` (MySQL and MariaDB), `sqlite`; `plan()` for a version, `create()` for a fresh database |
| `SchemaSnapshot` | a diff for a directory, written as a version (and a code skeleton for a custom one) |
| `SchemaVersionFile` / `SchemaDirectory` | one version on disk, checked against its name; the folder, in version order |
| `SchemaInspector` | what a live database has; "is this step already there"; "does the database match this model" |
| `SchemaHistory` | `winter_ppa_schema_history` of one owner (the config's class name) and the schema lock |
| `SchemaMigrator` | fresh / baseline / pending, one transaction per version |
| `VersionCode`, `#[SchemaVersion]` | the code of a version: `before()`, `after()` |
| `RenamedFromCleaner` | removes a recorded `#[RenamedFrom]`, token by token |
| `SchemaCheck` | what a server would not build as declared (indexes): errors and notices, before anything runs |

## The model

```
table => [
    'columns'     => name => ['name', 'type', 'nullable', 'default'] (+ 'detached' => true),
    'primaryKey'  => list<column>,
    'indexes'     => name => the CREATE INDEX statement,
    'constraints' => name => ['kind' => 'check'|'foreign', 'sql' => the ALTER TABLE … ADD CONSTRAINT],
]
```

Types, indexes and constraints are the SQL the mapping already generates (`Column::$type`,
`Index::toSql()`, `ForeignKey::toSql()`, `CheckConstraint::toSql()`) — the text `call db sql`
shows. So a snapshot belongs to its driver (`"driver"` in the JSON; another driver is refused), and
a change to how the mapping spells a type **is a schema change** for every application: the next
snapshot records it. Keep generated SQL stable.

A column keeps its place on a rename or a change, as the database does. Without that a fresh
database and an upgraded one list their columns in different orders — the first prototype did.

## Beside the tables: schemas and extensions

A PostgreSQL schema the tables live in (not `public`) and an `#[Extension]` of the config are
recorded as `createSchema` / `createExtension`, first in their version, and made first on a fresh
database (`SchemaModel::objects()` folds them; the table model does not hold them). Existence is
read before (`SchemaInspector::isApplied()`). A schema is never dropped; an extension no longer
declared stays — `--drop=extension:<name>` drops it (`dropExtension`, last in its version, no
CASCADE: what still uses it fails the version).

## What a server would not build

`SchemaCheck::tables()` runs in `SchemaSnapshot::diff()` (and the kernel's `db sql` / 4.x
`db migrate`): an error is what would fail on the server or mean something else, a notice what is
left out and only costs speed or size. `Index::toSql()` leaves out what a dialect has not —
MySQL / MariaDB: B-tree only, no WHERE / INCLUDE / operator class; SQLite: no USING / INCLUDE /
operator class — instead of writing it wrong; the check says so. An index of another method than
B-tree has the method in its name (`orders_note_gin_idx`).

## What a diff refuses

It never guesses; each refusal names what to write.

- a column gone and another new → a rename only with `#[RenamedFrom('old')]`; a table the same,
  with the attribute on its entity class (`renameTable`, first in its version; what is named after
  the table renamed with it — paired by definition — so an upgraded database names it as a fresh one);
- `#[RenamedFrom('x')]` whose `x` is not a column of the last version, or is also declared → error;
  one already recorded (`renameColumn` in a version) → a notice, and `stale` for `snapshot clean`;
- a column or table gone → `--drop`, or `--keep` (the column stays in the database, `detached` in
  the model: later diffs leave it alone, a fresh database does not get it);
- a NOT NULL column with no default added to an existing table → error (its rows have no value);
- a type change that is not a widening, a primary key change → only in a custom version, `"by": "code"`;
- what the driver cannot do itself → `SchemaSnapshot::diff()` tries `SchemaSql` on each change and says
  so. SQLite's ALTER TABLE limits are no such thing: the migrator rebuilds the table (below).

Widening (`SchemaDiff::widens()`): a longer VARCHAR, VARCHAR → TEXT, SMALLINT → INT → BIGINT, a
DECIMAL with as many digits on each side of the point or more. An identity / AUTO_INCREMENT that
appears or goes is not a widening; one that only changes how it is generated — `GENERATED BY
DEFAULT` ↔ `ALWAYS` (`#[Id(always: true)]`) — is the kernel's (`SchemaDiff::identityMode()`,
`SET GENERATED`).

Order of a version's changes (`SchemaDiff::ORDER`): constraints and indexes that go, renames, new
tables, new columns, changed columns, primary keys, detached / dropped columns, dropped tables, new
indexes, new constraints. A foreign key comes after the table it points at; a dropped table loses
its constraints first.

## Applying

`SchemaMigrator::migrate()` holds the schema lock for the whole run:

1. refuse if a version applied here changed (checksum of `.json` + `.php`), lost its files, or a
   version older than the last applied one was never applied;
2. no history and none of the history's tables → **fresh**: `SchemaSql::create()` of the last
   model, every version recorded `created`, no code run;
3. no history but tables → **baseline**: the latest version whose model the database matches is
   recorded with the ones before it; none matches → refused with the differences;
4. each pending version: `before()` → its steps, each skipped if `SchemaInspector::isApplied()`
   says it is there → `after()` → `SchemaInspector::compare()` with the version's model → its row.

PostgreSQL and SQLite: one transaction per version, its row inside it. MySQL / MariaDB: schema
changes commit at once — the row is `running` during the version and `failed` if it throws; the
next run starts it again, its done steps skipped — `running` left behind (the process killed) is
said with a warning. Each step is one statement there (a table rename with its indexes too), so a
stop never leaves a step half done. The version's code runs again in full: on MySQL / MariaDB write
it to bear that (`UPDATE … WHERE x IS NULL`, `INSERT IGNORE`). A failed version may be edited: only a
version recorded as done is checked against its checksum.

## Drivers

| | PostgreSQL | MySQL / MariaDB | SQLite |
| --- | --- | --- | --- |
| transaction per version | yes | no (DDL commits) | yes |
| lock | `pg_advisory_lock` (`lock_timeout`) | `GET_LOCK` | none (the writer takes the file) |
| alter a column | TYPE / SET / DROP each | `MODIFY COLUMN` | the table rebuilt |
| foreign key / check on an existing table | `ALTER TABLE` | `ALTER TABLE` | the table rebuilt (`ADD CONSTRAINT` is new to SQLite: 3.54 has it, the SQLite PHP ships on most servers does not, and a version is applied by any); inside CREATE TABLE when the version creates the table |
| drop a constraint, change the primary key | `DROP CONSTRAINT` | `DROP FOREIGN KEY` / `DROP CONSTRAINT` | the table rebuilt |
| an auto-incremented id | identity | `AUTO_INCREMENT` | `INTEGER PRIMARY KEY AUTOINCREMENT` — the whole primary key only |
| history table | in `getSchema()` | the database | the file |

**SQLite rebuilds** (`SchemaSql::rebuilt()` / `rebuild()`): a table with a change ALTER TABLE cannot
make — a column changed, a check or a foreign key added or dropped, the primary key — is made anew
from the version's model, after the version's other steps and before `after()`: the new table
beside it, the rows copied (the columns both have), the old one dropped, the new one renamed, its
indexes made. Foreign keys are off around the version's transaction (a `DROP TABLE` with them on
deletes, or cascades into, the rows pointing at it) and `PRAGMA foreign_key_check` must find none
broken before it commits. A narrowing or a primary key still asks for a custom version, as on every
server: the code moves data, the rebuild makes the table.

What `SchemaInspector` leaves out because the server made it: PostgreSQL's indexes behind primary
key / unique constraints; MySQL's index named after a foreign key; MariaDB's CHECK named after a
JSON column (its JSON is LONGTEXT + CHECK — `canonical()` treats `json` and `longtext` as one on
`mysql`). MySQL reports BOOLEAN as `tinyint(1)` — told apart before display widths are dropped.

Constraints are compared by name on every driver — SQLite's read from its CREATE TABLE, so a
rebuild in a version's code names them as the model does (`CONSTRAINT <name> CHECK …`).
Type comparison uses `SchemaInspector::canonical()`; defaults are not compared (each server
rewrites them: `'0'::numeric`, `now()`…).

## Testing

`tests/Schema/Migration/MigrationScenarios.php` — the same scenarios on every driver: fresh, upgrade
with data and code, fresh == upgraded, a version that fails and is fixed, code that leaves the
database wrong, an edited / missing / late version, a baseline, the history's copy, the lock.

```bash
PPA_PG=127.0.0.1:55432:spike:postgres:test \
PPA_MARIA=127.0.0.1:53307:spike:root:test \
PPA_MYSQL=127.0.0.1:53306:spike:root:test \
XDEBUG_MODE=off ./vendor/bin/phpunit tests/Schema
```

Without the variables those classes are skipped; SQLite always runs. A version's code in a test
gets a class name of its own (`MigrationScenarios::code()`): a process cannot declare a class twice,
and the scenarios run per driver in one process. For the same reason a generated skeleton puts the
version in the class name (`V003_FillStock`).

## What must stay true

1. **The entities are the only source of the schema.** A version records changes the diff
   computed; nothing in it is typed by a person except its code.
2. **A version never changes once a database applied it** — the checksum says so.
3. **A fresh database and an upgraded one end with the same schema.** The scenario
   `test_a_fresh_database_and_an_upgraded_one_have_the_same_schema` compares them column by column.
4. **No step is run to find out it is not needed**: existence is read, not provoked — no
   "already exists" in the server's log.
5. **Nothing here reaches for a framework** (invariant 1 of README): the migrator gets a `CDO`, a
   folder and a logger.
